This crate is supposed to serve as a compile time validated abstraction for data.
The system is abstracted as follows:
1. Models have a set of auxiliary tables that separate data from the models themselves, allowing for easy lookup and separation of concerns. This provides a faster query experience that can be optimised for user defined use cases. the auxiliary tables are as follows:
a. Primary: This table holds the main model and is used to directly query items. Models have a defined Primary key with themselves being the stored values. this is a simple K -> V table
b. Secondary: This table holds a secondary key with which to query the models. This allows for faster operations across property queries as only two jumps are necessary; fine the primary keys matching the query, then find the models with the primary keys. This is a multimap table as many primary models can hold the same secondary key.
c. Relational: This table holds related models to a main model. Here the relations are defined by their route and this can tell the compiler that if a related model is out of the compilation scope, then the model can pjysically not holf a relation to that item. This should toggle between multimap and single kv tables.
d. Blob: This table holdls large data. Blobs are types that can be chunked according to one of two stratefies: arbitrary serialisation chinking and field level, nested chunking. This allows users to decide how to load data from the store without needing to serialise the entire type. Chunks are tuple structs/enums that store the chunk alongside the index, and depending on the strategy, it is either a struct or an enum. if there is field level chunking, it is an enum, otherqise, arbitrary chunking is struct tuples.

Subscription: This is supposed to represent a semantic grouping of objects that are supposed to be kept in sync over a decentralised network. the idea here is to have subscriptions parallel operations made to main tables so that a merkle check can be done tosafely ensure that two nodes have the same copy of data and sync. unlike the other tables, Subscriptions can be defined at different levels of the database abstraction, depending on the scope of items the developer wants to be aware of the subscription. i) model level subscriptions are treated similar to any other table in that the model owns and manages the update behaviour of a subscription and direct operations are held there. ii) Definition level subscriptions are inserted into the static dispatch enum that is used to indicate that models in a definition are allowd to subscribe to this subscription. The idea is to create two main operation modes:

1. Sharding:
In the sharding, a model creates a physical table per auxiliry table abstraction and they are grouped semantically by the model itself. There should be a struct that represents a model table, and all table operations should be held against that struct. Having a model struct hodling tables can clearly deliniate the ownership of the operations and makes it much easier to define and manage how auxiliry tables should behave on certain operations. This should also be abstracted in the same way that they underlying tables are abstracted so that there is a simple passthrough of behaviour. for example, if an insert occurs, the table dispatches that insert operation on all the underlying tables as well, unless the operation configuration defines otherwise. For the case where a related table is affected by an operation and that table needs to be opened in a separate transaction, the operation should simply onlt work in the scope that the affected table live in. If ModelA relates to modelB in a different definition (it should not actually be possible to break repository boundaries), then the insertions shouold be from the Repository enum, not below. this fulfils static dispatch and quite clearly indicates the scope of the transaction.

2. Linear:
In linar mode, a model keeps one table, but stores all the various keys and values in enums that safely define the expected type of the items for that table, so that one type is used for the table defintiions and prefix pruning can be used to group key fetches.
